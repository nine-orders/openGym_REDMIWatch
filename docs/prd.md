# 开炼产品需求

## 目标用户

使用红米 Watch 5 训练，平时不方便使用手机，主要在电脑上管理 openGym 计划和训练历史的人。

同时面向习惯在手机 openGym 开始训练、希望使用手表查看及记录训练进度的人。两类用户共享手表 App，但选择不同的训练方式，不以手机在线为独立训练的前提。

## 电脑配对与离线训练

1. 用户在电脑 openGym 创建多套动作单，生成 8 位配对码。手表首次配对时选择「电脑配对」，分两步输入电脑 IP 和配对码后下载计划。
2. 用户离开电脑后，可以在手表上从已下载的动作单中任选一套，记录训练重量和次数。练完点「保存并同步」。服务器不可达时，手表应暂存整场记录，并在首页显示待同步场数。
3. 恢复与电脑服务器的连接后，用户打开手表 App，积压记录自动补传。训练历史应保留原始训练时间、动作、组数、重量和次数。传输重试不得产生重复记录。
4. 目标是支持约半个月后集中同步。按每天训练一次计算，真机验收至少需保存 15 场；15 场是验收量，设备可存的最多场数有待实测。

## 手机中转

配对页可选择手机配对，支持自动连接和手动输入 IP、配对码。手表存开练、记组、结束等事件，由安卓 App 写入训练历史。手表待发队列上限为 600 条事件，手机收件箱上限为 1,200 条。收件箱满时，未确认事件由手表后续重试。积压超过 200 条需要支持协议 3 的手机 hub。

## 首页重构（2026-11-26 需求）

当前验收版本为手表 **1.0.10**（内部版本号 11），搭配 1.0.8 手机端。V4 首页提供独立训练、手机同步、连接管理和待同步记录入口。1.0.10 修复动作单列表无法上下滑动的问题。实现范围与待实测项见[首页实施记录](watch-home-v4-20261126.md)。

### 1. 目标与信息架构

- 打开 App 首先进入训练启动台，而不是动作单列表；动作单只是独立训练的下一步，不是使用手表的必经前置条件。
- 连接对象（电脑/手机/离线）与训练方式（独立/同步手机）解耦。用户自行选择训练方式；手机开始训练或恢复连接均不应让首页自动跳转。
- 首页从上到下依次显示品牌与设置、设备连接状态、独立训练卡片、同步手机卡片、待同步记录提示。优先采用纵向布局，争取核心入口一屏可见；真机尺寸、可读性及触控区域须实测。

### 2. 首页排版与品牌

| 区域 | 内容及交互 |

### 3. 训练方式及状态流转

**独立训练：** 手表主导会话，选择动作单后开始记录重量、次数、组数和休息；可使用已下载的本地动作单离线训练，无需手机在线。记录按现有机制保存并同步。手机正在训练不应禁用独立训练。同步手机与独立训练的会话须区分身份，不能误覆盖或混入另一场训练的数据；同一场同步会话的事件必须去重。

**动作单列表：** 当动作单超出一屏时，列表支持上下滑动。标题和返回按钮固定。滑动到最后一项后，可以点选并进入对应训练。

**同步手机：** 手机主导会话，用户主动进入同步入口才加入手机当前训练。允许同步手机自由训练，不能要求手机先有动作单才能加入。同步应反映手机当前动作、组数、重量、次数及休息状态（以实际手机训练模型支持的字段为准），并允许现有协议支持的手表记录操作。

| 场景 | 手表预期行为 |
|---|---|
| 手机已经训练，用户打开手表 | 留在首页，「同步手机」显示手机训练中。 |
| 手表停留首页或浏览动作单，手机开始训练 | 更新手机训练状态，不强制跳转或覆盖当前选择。 |
| 主动点击「同步手机」，手机已有进行中会话 | 查询最新快照，允许加入当前训练；不要求再选择动作单。 |
| 主动点击「同步手机」，手机未开始训练 | 显示等待手机开始训练；已主动选择同步模式后，允许在手机开始时进入对应会话。 |
| 手机训练结束 | 同步会话反映结束状态；首页不再显示训练中。 |
| 未连接手机而点击「同步手机」 | 引导连接手机；若当前连接电脑，提示切换；不影响独立训练。 |
| 手机与手表各自开始训练 | 保留独立会话，不自动合并或覆盖；并行会话的协议支持及冲突处理须专项验证。 |
| 同步训练中断线 | 保留会话及未确认记录，重连后恢复并校验会话身份，避免重复记组或覆盖新会话。 |

同步卡片的建议状态文案：需要连接手机、切换至手机连接、等待手机开始训练、手机训练中、同步异常（点击重试）。连接失败或快照未知时不得误报手机没有训练；已缓存状态需与实时状态区分。

### 4. 配对与连接管理

- 首次使用保留电脑优先配对，并提供手机配对选择；已配对后自动尝试恢复上次使用的设备。配对/通信失败不阻塞已有本地动作单及独立训练。
- 首页显示设备状态并提供快捷切换；连接管理页提供电脑配对、手机配对（自动/手动）、重试及连接诊断。设置可提供设备管理及解除配对等低频操作。
- 设备状态至少区分未配对、连接中、电脑已连接、手机已连接、已保存连接但离线、通信异常。只有应用层握手/有效业务应答成功才能显示对应设备已连接；系统通道已建立或本地保存配对信息不等于业务可用。
- 切换设备不能删除待同步记录或中断后丢失训练数据。离线积压记录的归属、目标接收端及跨设备转移规则需基于现有协议核实，不能未经确认将原设备会话上传到另一档案。
- 暂按单一活动连接通道设计；不新增电脑与手机同时在线的硬性要求。

### 5. 待同步训练记录

首页以用户能理解的训练场数展示积压，而不是底层事件条数。底部提示应始终有明确状态，存在待同步或同步异常时提高视觉优先级，不遮挡训练入口。

| 状态 | 建议提示文案 |
|---|---|
| 无待同步记录 | 已全部同步（须以可靠队列状态为依据） |
| 已在本地持久化但未完成上传 | N 场训练待同步 |
| 上传进行中 | 正在同步 X/N 场 |
| 上传失败 | 同步失败，点击重试 |
| 本地存储接近上限 | 本地存储即将满，请同步 |

- 恢复有效连接后自动补传，并提供手动同步/重试入口。离线记录持续保存在本地；收到目标接收端符合协议的持久化确认后，才移出对应待同步队列。
- 部分成功时按实际未完整确认的场次更新数量，不能因为已上传部分事件就清空整场提示；重复传输不得产生重复训练记录。手机收件箱持久化与最终写入训练历史的确认语义须核实，不能误报已全部同步。
- 同步失败通常不阻止新训练；确实无法继续可靠保存时应明确提示，不得静默丢失记录。容量预警阈值需结合真机容量和协议队列限制确定，不能将 600 条事件等同于固定训练场数。
- 待同步详情页的设计建议：场数汇总、各场训练名称/日期/组数、待同步状态、立即同步/重试。字段可用性和按场汇总实现待验证；界面中的 3 场、54 组仅为示例，不是实际数据或容量指标。

### 6. 设置

首页保留高频操作，右上设置负责低频配置。包含设备管理（配对与解除配对）、连接诊断（系统通道、GET/POST、业务应答/超时）、本地存储（待同步场次、队列及容量）、关于应用（版本及开源信息）。用户已确认本轮纳入默认休息时间（配置组间休息时长）和振动提醒（休息结束时振动开关）；设置须持久化并在后续适用的训练中生效，手机同步训练应尊重当前会话的实际休息状态。默认值、可选时长及设备振动能力需结合现有实现确认，不额外要求主题切换或复杂同步策略。

## 手机通信故障与回归要求（2026-11-26）

用户报告：电脑连接能获取动作单；手机已有动作单，但手表显示「手表还没有手机动作单」；GET 和 POST 都出现看门狗超时；手机正常开始训练，手表不显示进行中状态。这些现象应联合排查手机应用层通信、快照发布/读取与会话状态同步，而不是简单延长超时或将其解释为没有动作单。

已有修复及实测记录见[手机同步故障修复](phone-sync-fix-20261126.md)。该记录表明：已修复系统通道误发 HTTP reason phrase、手机快照发布条件与监听恢复等问题；1.0.8 进一步修复小米 SDK 权限对象判断导致的监听未注册。1.0.8 手机 APK 与现有 1.0.7 手表的自动配对、快照读取、事件上报已通过真机复测，用户确认自动连接恢复；1.0.8 RPK 真机显示、锁屏重连及新版首页交互仍需验收。不能把已恢复通信等同于所有手机训练流程已验收。

回归要求：系统通道 GET/POST 有效应答；手机现有动作单能读入；快照发布不依赖错误的安装检测；手机开练、记组、结束后可获取最新状态；系统连接但业务超时时正确提示；断线、授权/监听失败及重启后可恢复；缓存与新快照不互相错误覆盖；电脑直连及离线批量补传不退化。系统通道与手动 HTTP 路径分别测试。
